# Plan: Player data from an H2 database

Amends `specs/player-profile-search/plan.md`. Everything not mentioned here (search rules, controller shape, error handling, `NameNormalizer`, exceptions, FrontEnd structure) stays as it is.

## Approach

At startup, a database initializer (1) creates the schema in an H2 **file** database from a script derived from `donneesStats.sql`, (2) checks whether the data is already there, and (3) if not, imports `data/donneesStats.json` in a single transaction. The application then reads the players through JPA entities mapped on the tables and on the tournament view; `PlayerService` keeps the in-memory search over the 1039 players. The JSON adapter, the `Clock` and the `database` profile disappear.

Main trade-offs:
- **JDBC for the import, JPA for the reads.** The import writes about 10,000 rows with explicit identifiers taken from the file: batch `JdbcTemplate` inserts are the simplest and the fastest way. The reads map to entities (the user asked for entities and views), with no write path in JPA.
- **The schema is a script (`schema.sql`), not generated by Hibernate** (`ddl-auto=none`): the structure stays under our control and close to `donneesStats.sql`.
- **The search stays in memory** (filter and sort in `PlayerService` on `findAll()`): 1039 players, one source of logic, no SQL collation difference. The `search_name` column of the previous adapter is dropped.

## Decisions to confirm

- **D1 - Schema deviations from `donneesStats.sql`.** The script is PostgreSQL; the H2 script follows it table by table with these deliberate differences, each forced by the data or by H2:
  1. `team` gets `fifa_code CHAR(3) NOT NULL` (the file provides it, the SQL schema has no column for it, and FR-11 shows the code).
  2. `player_match_stats` gets `is_goalkeeper BOOLEAN NOT NULL DEFAULT FALSE` (the file gives it per match; the SQL deduces goalkeepers without storing them; it feeds "goalkeeper matches" of FR-11).
  3. `referee.country_code` becomes nullable (the file gives the referee name only).
  4. The partial unique index `uq_player_stats_motm` (one man of the match per match) is not created: H2 has no partial index. It is checked by a test instead (the file has exactly one per match).
  5. PostgreSQL syntax is adapted (`SERIAL` to identity columns, `TIMESTAMPTZ` to `TIMESTAMP WITH TIME ZONE`, `CHAR(1)`/`CHECK` kept). Identifiers that are H2 keywords (`minute`) are handled with `NON_KEYWORDS=MINUTE,VALUE` in the connection URL (`match` is not reserved in H2 2.x).
  6. `CHECK (col IN (...))` becomes `CHECK (col = ANY (ARRAY[...]))` for `match.stage`, `booking.card` and `team_match_rating.result`: with H2 2.4.240 an `IN` list in a check constraint is rejected as invalid once the creating session is closed (every later insert fails).
- **D2 - Tournament view.** `v_player_tournament_stats` of the SQL uses `CROSS JOIN LATERAL`, which H2 does not support. It is rewritten with a pre-aggregated bookings sub-query (same columns, same results, `COALESCE` replacing the lateral always-one-row). `v_team_tournament_stats` is not created (no team screen yet), and a view for goalkeeper and captain matches is folded into the player view (two extra columns `goalkeeper_matches`, `captain_matches`).
- **D3 - Old data files.** `data/players.json`, `data/teams.json` and the old `data/README.md` content (about `players.json` / `matches.json`) are no longer used. They are **left in the repository untouched**; only the code that reads them is removed. `data/README.md` gets a section describing `donneesStats.json`, `donneesStats.sql` and `data/h2/`.
- **D4 - Contract break.** The API changes (integer id, new statistics, fields removed). BackEnd and FrontEnd change in the same feature and are delivered together; there is no API versioning.
- **D5 - Tests never write `data/h2/`.** Tests use in-memory H2 databases (a test `application.properties` sets the datasource URL), so they cannot lock or create the local file.

## Components

### Database (new package `stats_foot.stats_foot.database`)

| Element | Role |
|---|---|
| `src/main/resources/db/schema.sql` | H2 DDL: tables of parts 1, 2 and 4 of `donneesStats.sql` (with D1), indexes, and the view `v_player_tournament_stats` (D2). Every statement is `IF NOT EXISTS` / `CREATE OR REPLACE`, so it can run at every startup. |
| `DataFileImporter` | Reads `donneesStats.json` (Jackson 3, `tools.jackson`) and inserts, with batched `JdbcTemplate` calls and the identifiers of the file: competition, teams (name, FIFA code), players, stadiums and referees (deduplicated by name/city and by name), matches (score per period, penalty score, kickoff with offset), line-ups, substitutions, goals, bookings, penalty kicks, player and team match ratings (`algorithm_version = 'v1'`) and player and team match statistics. Identity columns are restarted after the import. |
| `DatabaseInitializer` | A `SmartInitializingSingleton`, so it runs after the beans are created and **before the web server starts**. Runs `schema.sql`, then, if `SELECT COUNT(*) FROM player` is `0`, runs `DataFileImporter` inside one `TransactionTemplate` (FR-5: rollback on any error; the DDL stays, the data does not, and the next startup imports again). Any exception is caught and stored in `DatabaseStatus` (FR-16): the application keeps running. |
| `DatabaseStatus` | Holds the startup failure, if any. `JpaPlayerRepository` checks it before each read and throws `PlayerDataUnavailableException`. |

## Data model and contracts

`GET /api/players?name=rangel` returns `200`:

```json
{ "total": 1, "truncated": false,
  "players": [ { "id": 1, "name": "Raul RANGEL", "teamCode": "MEX", "teamName": "Mexico" } ] }
```

`GET /api/players/1` returns `200`:

```json
{ "id": 1, "name": "Raul RANGEL", "teamCode": "MEX", "teamName": "Mexico",
  "goalkeeperMatches": 5, "captainMatches": 0,
  "stats": { "matchesPlayed": 5, "matchesStarted": 5, "minutesPlayed": 438,
             "goals": 0, "penaltyGoals": 0, "ownGoals": 0, "yellowCards": 0, "redCards": 0,
             "foulsCommitted": 0, "freeKicksWon": 0, "freeKicksConceded": 0,
             "duelsWon": 5, "duelsLost": 5, "corners": 0, "offsides": 0, "distanceKm": 25.11,
             "manOfTheMatchCount": 0, "rating": 6.9, "ratingWeighted": 6.9 } }
```

Errors, in English, unchanged: blank or missing `name` `400 "Please enter a player name."`; unknown or non-numeric id `404 "Player not found."`; unreadable database or failed import `503 "Player data is currently unavailable."`.

Database tables (D1): `competition`, `team`, `stadium`, `referee`, `player`, `match`, `match_lineup`, `substitution`, `goal`, `booking`, `penalty_kick`, `player_match_rating`, `team_match_rating`, `player_match_stats`, `team_match_stats`, and the view `v_player_tournament_stats`. Facts checked on the file: 1 competition, 48 teams, 1039 players, 104 matches, 16 stadiums, 42 referees, 3288 line-ups, 1000 substitutions, 308 goals, 282 bookings, 40 penalty kicks, 3288 player rows and 208 team rows of statistics, exactly one man of the match per match, and every player's `tournament` block equals the sums of their per-match rows (so the view must reproduce the file's totals).

## Tests (derived from the acceptance criteria)

All tests use the real `data/donneesStats.json` (versioned) and in-memory H2 databases; expected values are read back from the file by the test with an independent parse.

- **Importer and schema** (`DataFileImporterTest`, no Spring context, a plain in-memory `DataSource`): tables and columns exist (AC-1); row counts equal the counts of the file for every table (AC-2); a player's match rows and minutes sum equal the file (AC-3); one man of the match per match; a data file path given explicitly (AC-7).
- **Initializer** (`DatabaseInitializerTest`): empty database gets imported; second run on a filled database imports nothing and duplicates nothing (AC-5); a file corrupted halfway (copy in a `@TempDir`, truncated by the test) leaves zero rows and the next run with the full file imports everything (AC-6); an unreachable database or missing file stores a failure and does not throw (AC-17).
- **View** (`PlayerTournamentStatsViewTest`): for every one of the 1039 players, the view equals the `tournament` block of the file (AC-8), nulls included (`rating_weighted` null for players without minutes).
- **Repository contract** (`JpaPlayerRepositoryContractTest`): 1039 players; `findById` returns the identity, team and totals of reference players (id `1` goalkeeper with 5 goalkeeper matches, id `2` captain with 3 captain matches, id `316` with a null weighted rating); unknown id gives empty (AC-9, AC-13, AC-14, AC-16).
- **Service** (`PlayerServiceTest`, `PlayerServiceProfileTest`): `rangel`, `RANGEL`, `  raul   rangel  ` find id `1` (AC-10); boundary queries `so` (exactly 50, not truncated) and `te` (exactly 51, truncated) and `a` (913); no result; blank input; non-existent id; zero stays `0` and null stays null (AC-14).
- **API** (`PlayerControllerTest`, `ApiExceptionHandlerTest`): search results without `position` (AC-12); profile content and absence of every removed field and of `goalkeeperStats` (AC-13, AC-15); unknown and non-numeric ids give 404 (AC-16); 503 on a failed database (AC-17); English messages (AC-18).
- **Context** (`StatsFootApplicationTests`, `StartupImportTest`, `NoJsonSourceTest`, `DatabaseFilePathTest`): the application starts with an in-memory database and imports; the application starts with an unreachable database and answers 503; no class refers to `players.json` / `teams.json` (AC-9, checked by a source scan test); the local file `data/h2/` is created by a default start and is ignored by git (AC-4, checked by a review step rather than a test that depends on git).
- **Angular** (Vitest): service, `PlayerProfileCard` (all 19 totals, `0` against "not available", no removed field, no goalkeeper block) and `PlayerSearchPage` (list without position, same messages) on stubs shaped like the new contract.

## Risks and alternatives rejected

- **H2 keywords** (`minute`, possibly `match`) and PostgreSQL syntax in the DDL: handled with `NON_KEYWORDS` and `MODE=PostgreSQL`, verified at the first build; if a statement cannot be adapted it is rewritten and noted.
- **Hibernate opens a connection at boot**, which would crash the application when the database is unreachable (AC-17): mitigated by the metadata-access setting and an explicit dialect, covered by a context test with an invalid URL.
- **DDL commits implicitly in H2**: the "is the database filled" test is made on the `player` row count, not on the file's existence, and the import transaction only covers the data.
- **File lock**: two processes cannot open `data/h2/statsfoot` together (application and a second launch). Tests use in-memory databases (D5).
- **Identifiers**: explicit ids from the file with identity columns: the identity is restarted after the import so later inserts do not collide.
- **Import time** (about 10,000 rows from a 4 MB file) is a one-off at first start, with batch inserts; later starts only run the idempotent schema script and one count.
- **The data-total view equals the file** only if the loaded rows are complete: guarded by the 1039-player comparison test.
- *Rejected:* running `donneesStats.sql` as is on H2 (PostgreSQL-only constructs, and it contains no data); in-memory database recreated at each start (decided against by the product owner); keeping `JsonPlayerRepository` beside the database (two models to maintain, decided against); pure JDBC for the reads (the user asked for entities); storing the tournament totals as columns copied from the file (would not follow the schema and would not be recomputable from the matches).
